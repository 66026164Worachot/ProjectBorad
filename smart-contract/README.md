# Smart Contract: งานต้นแบบ

โฟลเดอร์นี้เป็นต้นแบบแยกจากระบบจองและระบบชำระเงินเดิม ยังไม่ได้เชื่อม frontend, backend หรือ Supabase และยังไม่ได้ deploy ห้ามใช้กับเงินจริงจนกว่าจะตรวจสอบความปลอดภัยและทดสอบครบ

## ทดสอบบนเครื่อง

```sh
cd smart-contract
npm install --ignore-scripts
npm test
```

ชุดทดสอบใช้ Solidity 0.8.26 โดยเปิด optimizer และ `viaIR` ใช้ Ganache จำลองเชนในเครื่อง ไม่ต้องใช้ wallet หรือ ETH จริง การ deploy ภายหลังต้องใช้การตั้งค่าคอมไพเลอร์เดียวกัน

## แนวทางเชื่อมระบบเดิม

- บัญชี JWT ของเว็บและสิทธิ์ wallet บนเชนเป็นคนละระบบ ต้องยืนยันความเป็นเจ้าของ wallet ด้วยการเซ็นข้อความและผูกบัญชีอย่างปลอดภัย
- การจอง ราคา และสถานะเงินของการจองบนเชนให้ถือข้อมูลจาก contract เป็นหลัก เก็บข้อมูลติดต่อและข้อมูลประกอบใน Supabase โดยเชื่อมด้วย chain ID, contract address และ booking ID
- ตรวจสอบธุรกรรมและ event จากเชนหลังได้รับ confirmations ที่กำหนด รองรับการซิงก์ซ้ำและ chain reorganization ห้ามเชื่อข้อมูลสถานะที่ client ส่งมาเพียงอย่างเดียว
- ไม่ใช้การจองบนเชนและระบบเดิมจองโต๊ะเดียวกันโดยไม่มีวิธีป้องกันการจองซ้อนร่วมกัน ต้องกำหนดแผนแยกทรัพยากรหรือย้ายระบบก่อนเปิดใช้งาน
- ไม่ใส่ข้อมูลส่วนบุคคลหรือ hash ที่เดาได้ง่ายบน public chain โดยตรง ต้องออกแบบการเข้ารหัส/การทำ commitment และจัดการ salt ก่อนเชื่อมจริง

## ต้นแบบผูก wallet กับ Supabase

- `b end/migrations/001_wallet_and_chain.sql` เพิ่มตารางแยก ไม่แก้ตารางการจองเดิม ผู้ใช้ได้รัน migration บน Supabase แล้วและตรวจพบตารางกับฟังก์ชันผ่าน API
- `b end/routes/apiWalletRoutes.js` ให้บัญชีที่เข้าสู่ระบบด้วย JWT ขอข้อความ SIWE สำหรับ Sepolia และยืนยันลายเซ็นจาก wallet แบบ EOA โดย challenge มีอายุ 5 นาทีและใช้ได้ครั้งเดียวผ่านฟังก์ชันฐานข้อมูล ไม่รองรับ contract wallet แบบ ERC-1271 ในต้นแบบนี้
- `PUBLIC_WEB_URL` ฝั่ง backend ต้องตรงกับ origin ของเว็บไซต์ที่ผู้ใช้เปิด และต้องใช้ HTTPS นอก localhost/127.0.0.1
- `VITE_WALLET_LINK_ENABLED=true` เปิดส่วนผูกกระเป๋าหลังติดตั้ง migration การเชื่อม wallet ใน browser เพียงอย่างเดียวไม่ได้ยืนยันตัวตน
- หน้าทดลอง Sepolia ต้องกำหนด `VITE_SEPOLIA_CONTRACT_ADDRESS` เป็น address ของสัญญาที่ deploy ด้วย ABI นี้ แล้วรีสตาร์ต frontend หน้านี้ส่งธุรกรรมบนเชนแยกจากการจองเดิมเท่านั้น ยังไม่มี indexer หรือซิงก์การจองกับ Supabase

## สมมติฐานต้นแบบที่ต้องยืนยัน

- มัดจำขั้นต่ำถูกจำกัดไม่ให้เกินราคารวม เพื่อไม่ให้ยอดคงเหลือติดลบ
- ข้อพิพาทสถานะ Confirmed และ CheckedIn เปิดได้ตราบเท่าที่สถานะยังไม่เปลี่ยน ส่วน Completed และ NoShow ใช้ช่วงเวลาตามนโยบายหลังปิดงาน
- เงินส่วนที่ร้านมีสิทธิ์ได้รับจากการยกเลิกโดยลูกค้าและจากคำตัดสินข้อพิพาทเข้า `ownerWithdrawable` ทันที
- ค่า check-in ล่วงหน้าและเวลาเปิดร้านใช้ค่าปัจจุบัน ส่วนนโยบายที่ระบุใน `Policy` ใช้เวอร์ชันที่บันทึกเมื่อสร้างการจอง
- การคืนเงินเมื่อร้านหายตัวรองรับสถานะ Confirmed เท่านั้น กรณี CheckedIn แล้วไม่มีการปิดงานยังต้องออกแบบทางออกเพิ่มเติม

## งานค้างก่อนใช้งานจริง

- ขยายชุดทดสอบให้ครอบคลุม acceptance tests T1–T23, ขอบเขตเวลา, การส่ง ETH ไม่สำเร็จ, การโจมตี reentrancy, การเปลี่ยน policy และ invariants ทุกเส้นทาง
- ตรวจสอบการใช้ gas ขนาด bytecode และทบทวนการออกแบบ/ตรวจสอบความปลอดภัยโดยผู้เชี่ยวชาญอิสระ
- ตกลงนโยบายกรณีข้อพิพาทค้าง, ลูกค้าไม่จ่ายยอดคงเหลือ, ร้านไม่ดำเนินการหลัง check-in, การยกเลิก/เปลี่ยนโต๊ะ และธุรกรรมล้มเหลว
- จัดทำวิธี deploy และ verify สำหรับ Sepolia พร้อมการตั้งค่าแยกจาก production
- เชื่อม wallet, event indexer, ฐานข้อมูล, สิทธิ์ และหน้าจอระบบเดิมตามแผน
